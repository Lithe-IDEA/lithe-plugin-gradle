# Agent 笔记：Gradle 编译设置只编辑插件拥有的配置块

状态：已实现

## 先说结论

Gradle 的项目和编译事实仍由真实 Gradle 模型提供。设置页只在原始构建文件末尾维护一个明确标注、可验证的配置块，不尝试把任意 Groovy 或 Kotlin 脚本改写成自己的语法树。用户确认后才暂存修改，由宿主保护来源并原子发布。

## 为什么这样做

Gradle Tooling API 和 JavaCompile 任务能读取有效目标、参数、模块与继承状态，却没有把任意两种 DSL 安全改写回源文件的官方接口。执行任意脚本才能确定它的含义；用正则识别用户脚本、修改猜测出的任务或维护另一份编译模型都会破坏用户配置。只显示不生效的偏好也无法满足编译设置需求。

## 决策与边界

读取使用插件已有的 init script 和真实 JavaCompile 任务。写入保留原文件前缀，生成普通 Gradle 配置，并将插件自己的元数据和生成结果互相核对；配置块被改写或不再位于文件末尾时拒绝保存，要求重新读取并处理冲突。宿主只理解公开设置投影、来源身份和暂存回执，不理解 DSL。正确做法是对已捕获模块保存目标并重新调用 Gradle 编译；不要从 IDE 缓存推断 class 版本。

## 代价与迁移路径

这是有意限制的编辑范围，无法安全接管所有项目约定插件和自定义任务。若 Gradle 提供可保留注释、覆盖两种 DSL 的官方源码编辑接口，应改用它并迁移既有配置块；此前保留明确所有权和拒绝外部改写的规则。

## 验证方式

`scripts/compiler/test.mjs` 对 Groovy、Kotlin、父级继承和模块覆盖运行真实 Gradle，检查 Java 8/11 class 文件头、外部 JAR 编译与运行，删除覆盖后重新确认继承，并验证用户脚本前缀不变。进程与临时目录有界清理，源码和暂存不进入发行包或跨工作树缓存。
