# Agent 笔记：当前文件启动 Java 时使用 Gradle 源集

状态：已实现

## 先说结论

复杂 Gradle 工程能够用 Gradle 编译时，编辑器的 Java 语言服务器仍可能在准备运行时报告另一套编译错误。标题栏「当前文件」在需要时发现主类，由 Gradle 决定哪些编译任务和依赖属于这次启动。应用和调试进程由宿主管理。

## 问题

JUnit 5 的 `:junit-platform-console:classes` 能构建成功，原先当前文件动作走 JDT 的构建路径，却在编译阶段中止，无法到达断点。两条路径对编译目标、生成源码和模块依赖使用了不同的配置。

## 决策

提供者调用 JDK 编译器的语法树接口解析当前源码，在启动准备时使用 Gradle 实际求值的 Java 源集和 `runtimeClasspath`。让 Gradle 调用运行类路径依赖的构建任务。运行计划把类路径、入口和参数交给宿主，调试使用 Java Support 注册的调试适配器。这样已有的调试连接、停止和进程清理语义适用于当前文件和保存后的配置。

短类路径随启动参数返回。长类路径使用模块构建目录下的 manifest JAR，随 Gradle 清理。安装包中的后端和 init script 在运行期间只读。每次准备的临时导出文件在调用结束后删除，资源生命周期见 README。

## 考虑过的备选方案

让 JDT 在启动前完成编译会继续依赖导入模型能否复现项目自带的 Gradle 构建。将编译类路径加入运行类路径会带入仅供编译的依赖，也不能表达项目对发布产物重定位、打包或自定义启动参数的要求。项目已有启动任务时，构建工具窗口继续使用该任务的配置。

## 后果

发现主类只读取当前文件。如果文件没有唯一所属的 Java 源集，准备运行会要求用户选择有效的文件。准备阶段启动 Gradle，成本随项目的配置和编译任务增长。入口解析需要 JDK 17 或更新版本，应用 JVM 由宿主选择。

## 验证

`node scripts/test.mjs` 通过已打包的提供者发现入口，运行 Gradle 多模块项目并启动应用，同时验证编译失败和安装包字节不变。macOS 无头工作台在 Spring Petclinic 和 JUnit 5 的启动类命中 Java 断点，Petclinic 通过标题栏运行后返回 HTTP 200。

## 适用范围

标题栏「当前文件」及由该入口保存的 Gradle Java 配置。实现位于 `provider/` 和 `io.github.lithe-idea.gradle-build/lithe.run.init.gradle`。
